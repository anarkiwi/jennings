# Native core

`MPU(memory=NativeMemory())` runs the 6510 in Rust. Any other memory object keeps the
pure-Python deity-informant engine. Wheels ship the native core as `jennings._core`;
an sdist install (no Rust toolchain) has the Python engine only and
`jennings.memory.NATIVE` is false.

## Layout

| Path | Role |
|---|---|
| `crates/jennings-core` | Pure Rust library: `Bus` trait, `Cpu`, `FlatMemory`, `run_until`/`run_to_rts`. No PyO3. |
| `crates/jennings-core/src/cpu_gen.rs` | Opcode semantics, generated by `tools/gen_cpu.py`. Do not edit. |
| `crates/jennings-py` | PyO3 extension `jennings._core`: `NativeMemory`, `Core`. |
| `jennings/devices/mpu6502.py` | `MPU.__new__` returns a `NativeMPU` (py65 surface over `Core`) for a `NativeMemory`. |

## Generated semantics

`tools/gen_cpu.py` lifts every opcode with `deity_informant.lifter.lift` under two
sentinel sets (operand bytes and the zero-page pointer they name all differ between
sets). Each operand-derived constant is bound to an operand expression (`b1`, the word
`w`, `(b1+1)&$FF`, `(b2+1)&$FF`) from the lifter's own provenance map, and every binding
is checked to reproduce the lifted value under both lifts. A constant that differs
between lifts without provenance must be explained by a memory read the lifter made: the
only one is `$93 SHA (zp),Y`, whose `H+1` comes from the pointer high byte; it binds to
the P-Code `LOAD` of that byte. Anything else fails generation.

Each opcode becomes one `op_XX` function: operand fetches, the P-Code as straight-line
Rust (`LOAD`/`STORE` whose address derives from SP become stack accesses, the rest data
accesses), the base cycles plus the extra-cycle rule (`cross(base, X|Y)` for `ax`/`ay`/`iy`
penalties, `Cpu::branch` for taken/page-crossing branches) and the control kind. The
control kinds the lifter defers to `PcodeVM.step` (`br`, `jmp`, `jmpind`, `jsr`, `rts`,
`rti`, `brk`, `jam`) are resolved by one `Cpu` method each, mirroring `PcodeVM.step`;
no opcode body is hand-written. `tests/test_gen_cpu.py` checks regeneration is a no-op.

## Access classes

| Access | Examples | `subscribe_to_*` | `observe_data_access` | raster model |
|---|---|---|---|---|
| fetch | opcode, operands | no | no | no |
| data | operand reads/writes, `(zp)` pointer bytes | yes | yes | yes |
| stack | `PHA`/`PLA`/`PHP`/`PLP`, `JSR`/`RTS`/`RTI`/`BRK`, interrupt frames, driver dummy frames | yes | no | — |
| other | interrupt vectors, `JMP (ind)` pointer | yes | no | yes |
| host | `mem[addr]` from Python | yes | no | yes |

Subscriptions follow `ObservableMemory`: callbacks per address in registration order
(deduplicated by `==`), a read callback's non-None result substitutes the value (the last
one wins; memory is not read if any substitutes), a write callback's non-None result is
passed on and stored. `observe_data_access(on_read, on_write, reads=None, writes=None)`
calls `on_read(addr)` after each data load and `on_write(addr, value)` after each data
store (the instruction's value, before write callbacks rewrite it), optionally limited
to address sets; `mem.last_load` is the address of the most recent data load.

## NativeMemory

- `mem[a]`, `mem[a:b:s]` read through the page table, raster model and read
  subscriptions; assignment accepts ints, bytes-likes or int iterables and goes through
  write subscriptions. `mem.write(start, data)` copies into RAM with no callbacks.
- The buffer protocol exposes the 64 KiB RAM (`bytes(mem)`, `memoryview(mem)`,
  `numpy.frombuffer(mem, numpy.uint8)`), zero-copy.
- `set_page(n, image)` maps 4 KiB page `n` to a read-only 4096-byte image;
  `set_page(n)` maps it back to RAM. Writes always reach RAM (ROM under RAM).
- `mem.io` marks `$D000-$DFFF` as the banked-in I/O page; `raster_model(ntsc)` makes
  `$D011`/`$D012` follow the beam (`cycles // cycles_per_line % lines`, PAL 63×312, NTSC
  65×263) at the cycle count of the instruction's start while `io` is set, as
  `vagrant_moses.cpu.flat_mpu` does; `raster_model(None)` disables it.
- Python is called only for a subscribed or observed address.

## Drivers

`NativeMPU.run_until(max_cycles=None, stop_pcs=None, sp_above=None, stop_on_jam=True,
irq_period=None)` steps with the GIL released until, before an instruction, SP exceeds
`sp_above`, more than `max_cycles` have elapsed, or PC is in `stop_pcs`; or, after one, a
JAM ran or a callback set `mpu.stop = True`. It returns `"sp"`, `"cycles"`, `"pc"`,
`"jam"` or `"stop"`. With `irq_period`, the instruction that brings the cycle count to
`mpu.irq_due` is followed by `irq()` (dropped if I is set, as `MPU.irq()` does) and
`irq_due` advances by the period; it persists across runs (unset: one period from the
run's start), so a playroutine's IRQ cadence never returns to Python. `run_to_rts(pc, acc, max_cycles)` and `run_to_rts_until(pc, acc, pcs,
max_cycles)` are `vagrant_moses.cpu.run_to_rts` and `pysidtracker.emu.run_to_rts_until`
(dummy `$0100` return pushed, stop once SP rises above its start, `pcs` checked before
each instruction). `step()` remains correct for callers that step from Python; the
drivers are the fast path.

A driver claims its core and memory for the running thread. Other threads touching
either get `RuntimeError` until it returns; independent MPUs run in parallel threads.
Callbacks re-acquire the GIL, see the registers as at the start of the executing
instruction, and may not assign registers. An exception from a callback ends the
current instruction (with no further callbacks) and is raised from the driver or
`step()`.

## Differences from the Python engine

- Fetches never reach subscriptions; the Python engine reads opcode bytes through an
  `ObservableMemory` several times per step (JAM check, cache key, lift).
- `$93 SHA (zp),Y` uses the pointer it loads. `PcodeVM` caches the record on
  `(pc, opcode, operand bytes)` with `H+1` taken from the pointer at first lift, so a
  later pointer change at the same PC reuses the stale constant.
- The `(zp),Y` page-cross penalty uses the loaded pointer; `PcodeVM._resolve` re-reads
  it from memory after the instruction (equal unless a callback rewrites the pointer).
- Host writes must be bytes (`ValueError` otherwise); callback results are masked to 8 bits.

## Adopting NativeMemory

`vagrant_moses.cpu.flat_mpu`: build a `NativeMemory(ram)`, `set_page` the BASIC, KERNAL
and CHARGEN images per `banking($01)` and set `mem.io`, re-banking from one write
subscription on `$00`/`$01` (and a read subscription for `port_read`), and replace the
raster subscription with `mem.raster_model(ntsc)`. `run_to_rts` becomes
`mpu.run_to_rts(...)` when `mpu.native`.

`pysidtracker.emu`: drop the `mpu._vm` swap in `observe_data_access` for
`mem.observe_data_access(on_read, on_write, reads=..., writes=...)`; `SidWriteLog` can
observe only the SID writes and read `mem.last_load` instead of observing every load.
Its VM hook also reports `PHA`/`PLA`/`PHP`/`PLP` page-1 accesses (they are P-Code
`LOAD`/`STORE`); the native observer, per the hook's documented contract, does not.
`wire_mpu`'s SID subscriptions carry over unchanged. `run_to_rts_until` becomes
`mpu.run_to_rts_until(...)`.
